# Ice Snow City 高保真美术团队建设与资产交付指南

**版本：** 2026-09-16  
**适用项目：** Ice Snow City，16:9 移动端横屏、2.5D 伪 3D、冰雪主题城市模拟与 GameFi 场景  
**目标：** 建立一支能够持续交付高保真、可运行、可验收、可维护 3D 资产的美术团队，而不是只产出静态展示图的外包小组。

## 一、先明确团队要交付什么

优质美术团队的核心不是“模型看起来漂亮”，而是同时满足四个条件：视觉风格统一、移动端性能可控、资源能够正确接入 Babylon.js、交付证据足以通过项目门禁。Ice Snow City 当前已经拥有程序化 baseline，因此真实团队的任务不是重复制造占位物，而是以明确的视觉 DNA 替换最关键资产，并保留 baseline 作为降级方案。

> **重要边界：** 任何概念图、AI 生成图、灰盒模型或程序化 GLB 都不能自动等同于高保真资产。只有完成制作、技术清理、引擎接入、真机验证和版本审计的资源，才能进入 `verified` 或 `readyForRuntime` 状态。

### 1.1 Ice Snow City 的视觉 DNA

| 维度 | 统一规范 |
|---|---|
| 画面语言 | 2.5D 伪 3D；以等距或轻微俯视镜头阅读城市，不追求写实摄影，而追求清晰轮廓和远景识别度 |
| 形体 | 半写实卡通；大体块、干净切面、适度夸张的屋顶和檐口，避免过度复杂的小零件 |
| 冰雪特征 | 雪层具有厚度和堆积逻辑；屋顶、路肩、灯柱顶部和管线转角形成可识别积雪边界 |
| 材质 | PBR 为基础，控制粗糙度变化；冰面偏冷蓝、金属偏蓝灰、灯光使用暖色形成冷暖对比 |
| 色彩 | 主色为冰蓝、雪白、蓝灰；功能建筑使用少量金色、青绿或暖橙作为导航色，不使用高饱和杂色 |
| 光照 | 冷色环境光配合暖色功能灯；城市核心、银行、商业中心必须拥有远景可识别的光色或轮廓标识 |
| 资产识别 | 每个模型必须有标准视觉 DNA：轮廓、主色、功能符号、雪层规则、夜间灯光规则和 LOD 规则 |
| 性能原则 | 先保证移动端可读性，再增加细节；细节优先放在轮廓、材质对比和少量英雄部件，而不是无差别增加面数 |

### 1.2 第一批不可缺少的真实资产

建议首批只做能够显著提升“可玩场景完整度”的资产，不要一开始铺开全部 26 个资产。第一批应包含城市核心、银行、商业中心、生产设施、玩家角色、NPC、道路/街灯和植被环境八类资源。每一类先做一个可作为标准的代表资产，形成生产模板后再批量扩展。

| 优先级 | 资产 | 首批目标 | 原因 |
|---|---|---|---|
| P0 | 城市核心 | 1 个英雄级地标 | 决定玩家首次进入场景的识别度和世界观可信度 |
| P0 | 银行/金融区地标 | 1 个功能地标 | 支撑 GameFi 叙事、金融区任务和交易入口的空间记忆 |
| P0 | 商业中心 | 1 个功能地标 | 支撑收集商业数据、商业任务和城市经济循环 |
| P0 | 生产设施 | 1 个功能地标 | 支撑城市生产、建设和收益系统的视觉锚点 |
| P0 | 玩家角色 | 1 套完整可动角色 | 没有完整角色就无法验证移动、镜头比例和交互尺度 |
| P1 | NPC | 2 个外观变体，共用骨骼 | 支撑任务大厅、巡逻路线和城市活力 |
| P1 | 道路/街灯 | 1 套模块化道路包 | 连接场景、任务节点和地标，复用率最高 |
| P1 | 植被/雪地环境 | 1 套模块化环境包 | 解决空场景问题并建立冰雪都市基调 |

## 二、建议的团队结构

团队不应一开始就堆很多建模师。最小可行团队需要一个能够守住风格和资产门禁的人，以及能够把资产真正送进 Babylon.js 并在移动端跑起来的人。

### 2.1 推荐的最小核心团队

| 岗位 | 建议人数 | 主要职责 | 必须具备的能力 |
|---|---:|---|---|
| 美术总监/风格负责人 | 1 | 视觉 DNA、参考板、最终风格裁决、外包审核 | 能把抽象风格写成可执行规范；有完整项目落地经验 |
| 3D 角色/生物设计师 | 1 | 玩家角色、NPC、骨骼、蒙皮、基础动画协作 | 角色比例、拓扑、绑定、移动端优化 |
| 3D 环境/建筑设计师 | 1–2 | 地标建筑、道路、模块化环境、雪层设计 | 建筑模块化、LOD、碰撞、场景构图 |
| 材质/技术美术 | 1 | PBR、雪层材质、Shader、光照、性能预算 | Babylon.js 或相近引擎经验；能定位 GPU/材质问题 |
| 动画师 | 0.5–1 | 角色待机、行走、交互、任务动作 | 骨骼动画、循环动画、压缩和状态切换 |
| 美术制作人/资产经理 | 0.5–1 | 排期、任务拆解、版本、外包沟通、证据归档 | 能维护资产状态和交付清单，不只负责催进度 |
| 引擎整合/客户端美术程序 | 0.5–1 | GLB 导入、材质绑定、LOD、碰撞、性能采样 | Babylon.js、TypeScript、资源管线和移动端调优 |

最小团队约为 5–7 名全职等效成员。预算有限时，动画师和引擎整合可以采用稳定的兼职或按阶段合作，但**美术总监、技术美术和核心环境设计师不应完全临时外包**，否则容易出现风格漂移和资产无法落地的问题。

### 2.2 何时扩大团队

当第一批八类标准资产通过验收后，再增加道具、建筑变体、角色变体、特效和 UI 插画岗位。扩张依据应是资产队列和验收吞吐量，而不是“感觉人手不够”。如果每周新增资产多于技术美术能够验收和整合的数量，优先增加技术美术或资产整合能力，而不是继续增加纯建模人数。

## 三、招聘时如何识别真正合格的人

作品集只能证明候选人做过好看的东西，不能证明其能交付可运行资产。因此招聘必须采用“作品集 + 小型付费试题 + 技术审查 + 协作面谈”四段式流程。

### 3.1 角色招聘标准

| 岗位 | 作品集必须看到 | 面试重点 | 红旗信号 |
|---|---|---|---|
| 环境/建筑设计师 | 完整建筑、线框、贴图、LOD 或引擎截图 | 是否能解释模块化、比例、碰撞和性能取舍 | 只有渲染图，没有线框、面数和引擎结果 |
| 角色设计师 | 全身角色、拓扑、UV、骨骼或动画片段 | 是否理解移动端角色面部、骨骼和动画压缩 | 只有头像或概念图，没有完整角色交付 |
| 技术美术 | Shader、材质、性能对比、工具脚本 | 能否把艺术需求转成参数和验收指标 | 只会调效果，不会定位 GPU、内存或加载问题 |
| 动画师 | 循环待机、行走、交互、状态切换 | 动画是否自然、是否能在有限骨骼下复用 | 只展示短片，不提供帧率、骨骼或导出信息 |
| 美术总监 | 风格指南、团队案例、返工前后对比 | 能否给出明确取舍和书面规范 | 只会说“感觉不对”，无法写验收标准 |

### 3.2 推荐的付费试题

给候选人一个简化的“冰雪银行地标”题目：提供一张粗略平面尺寸、一组 Ice Snow City 色板和一个移动端性能预算，要求在 3–5 个工作日内交付概念图、低模/高模、PBR、LOD、GLB 和一页技术说明。试题必须付费，且只用于招聘评估，不得直接用于商业上线。

评审时按以下权重打分：视觉符合度 30%，模型和材质质量 20%，移动端技术合规 20%，可复用性 15%，文档和沟通 10%，按反馈修改能力 5%。若候选人拒绝说明面数、纹理尺寸、材质数量或导出设置，即使画面好看，也不应直接进入核心资产队列。

## 四、标准生产流水线

每一个真实资产都必须经过同一条流水线。这样才能把“艺术判断”与“可验证的技术交付”分开，避免在最后一天才发现模型无法加载或超出设备预算。

### 4.1 八个阶段

| 阶段 | 产物 | 负责人 | 通过条件 |
|---|---|---|---|
| 1. 需求冻结 | Asset Brief、功能、尺度、镜头距离、性能预算 | 美术总监 + 产品 | 功能和视觉目标没有歧义 |
| 2. 视觉探索 | 参考板、正侧背视图、色板、雪层规则 | 美术总监 + 设计师 | 选定唯一方向并记录否决方案 |
| 3. 灰盒验证 | 低细节模型、场景比例、摄像机截图 | 环境设计师 + 引擎整合 | 在 Babylon.js 中比例、遮挡、交互点正确 |
| 4. 高模与低模 | 高模源文件、游戏低模、拓扑说明 | 3D 设计师 | 轮廓稳定、无明显拓扑和法线问题 |
| 5. PBR 与雪层 | Base Color、Normal、Roughness、Metallic、AO、雪层参数 | 材质/技术美术 | 材质数量、纹理尺寸和色彩符合规范 |
| 6. LOD 与碰撞 | LOD0/LOD1/LOD2、碰撞体、遮挡策略 | 技术美术 | 距离切换稳定、碰撞体简洁、无穿透 |
| 7. 引擎整合 | GLB、材质绑定、动画、交互挂点 | 引擎整合 | 加载、渲染、点击、动画和资源释放正常 |
| 8. 设备证据 | iOS/Android 采样 JSON、截图、版本信息、报告 | QA + 技术美术 | 真机性能证据完整，才能申请高保真状态 |

### 4.2 推荐的资产状态机

```text
brief → concept-approved → greybox-approved → art-production
      → technical-review → engine-integrated → device-validated
      → verified → readyForRuntime
```

任何阶段失败都应回退到对应阶段，而不是通过改状态字段掩盖问题。`procedural-baseline`、`external-pending`、`technical-review` 和 `device-validated` 必须彼此区分。当前项目的程序化 GLB 只能进入开发预览或替代资源路径，不能绕过真实资产门禁。

## 五、每个资产的验收清单

### 5.1 艺术验收

模型必须符合 Ice Snow City 的视觉 DNA，远景轮廓在目标摄像机下可识别，主色和功能色与其他地标形成层次关系。雪层必须符合重力、风向和建筑结构，而不是简单地在所有表面覆盖同一层白色。角色必须提供完整全身模型、材质、骨骼和至少一组可循环动作；不能以头像或静态半身图替代。

### 5.2 技术验收

| 检查项 | 验收要求 |
|---|---|
| 文件格式 | GLB/glTF 2.0 可解析，文件头、版本和声明长度一致 |
| 节点结构 | 命名稳定，不包含无意义默认节点；交互点、挂点和出生点明确 |
| 材质 | PBR 参数完整，材质数量受控，透明材质单独说明排序和深度策略 |
| 纹理 | 纹理尺寸、压缩格式、色彩空间、命名和引用完整 |
| 几何 | 法线正确、无明显重叠面、无非预期孤立点、LOD 轮廓可接受 |
| 动画 | 起止帧、循环、骨骼命名和播放速率明确；无明显脚底滑动 |
| 碰撞 | 使用简化碰撞体，不把高模网格直接作为碰撞体 |
| 性能 | 在目标移动设备上记录 FPS、P95 帧时间、内存、Draw Calls 和加载耗时 |
| 安全 | 交付包不含 Token、Webhook、设备序列号、个人路径或未授权第三方资产 |
| 许可证 | 参考图、材质、字体、模型和插件均有来源与授权记录 |

### 5.3 建议的移动端预算起点

下表是**项目内部的起始预算**，不是对所有设备的保证。技术美术应根据目标机型实测后调整。英雄建筑可以拥有更高的 LOD0 预算，但屏幕同时可见的英雄级对象数量必须受到控制。

| 资源类别 | LOD0 起始三角形预算 | 纹理起始建议 | 材质建议 |
|---|---:|---:|---:|
| 英雄地标 | 25k–60k | 1–2 张 2048 或图集 | 2–4 个 |
| 普通功能建筑 | 8k–25k | 1024–2048 | 1–3 个 |
| 模块化道路/街灯 | 1k–8k | 512–1024 或图集 | 1–2 个 |
| 玩家角色 | 12k–25k | 1024–2048 | 2–4 个 |
| NPC | 8k–18k | 1024 | 1–3 个 |
| 植被小件 | 200–3k | 256–1024 | 尽量图集化 |

最终门槛必须以真实设备采样为准。若平均 FPS、P95 帧时间、峰值内存或 Draw Calls 未达到项目阈值，资产应回到 LOD、材质或场景整合阶段，而不是直接降低验收标准。

## 六、版本、文件和外包管理

建议采用“一个资产一个目录、一个版本一个不可变交付包”的方式。源文件、导出文件、截图、技术说明、许可证和验收报告必须能够由资产 ID 关联起来。不要只在聊天软件里传最终模型，也不要让最终文件只存在某个艺术家的个人电脑上。

推荐目录结构如下：

```text
art-delivery/
  landmark-bank/
    v001-brief/
    v002-concept-approved/
    v003-engine-integrated/
    v004-device-validated/
      landmark-bank.glb
      textures/
      screenshots/
      technical-report.json
      license-record.md
      sha256.json
```

每次交付必须包含 Asset ID、版本号、导出时间、制作人、软件版本、目标平台、GLB SHA-256、纹理清单、LOD 清单、动画清单、碰撞说明、已知问题和许可证说明。外包合同应明确源文件交付、商业使用权、第三方素材责任、修改次数、验收定义、保密义务和项目终止后的资料移交。

## 七、预算与合作模式

预算不应只按“一个模型多少钱”计算。真正成本包含概念设计、建模、材质、绑定、动画、技术清理、引擎接入、返工、QA 和管理。以下是内部规划用的三档模型，具体金额需根据地区、资历、合同和资产复杂度报价。

| 模式 | 适合阶段 | 团队形态 | 优点 | 主要风险 |
|---|---|---|---|---|
| 核心小队 | 原型到首批 P0 | 5–7 名核心成员 | 风格统一、沟通短、适合建立标准资产 | 个别成员离开会形成单点风险 |
| 核心小队 + 专项外包 | 首批资产扩展 | 核心负责 DNA 和验收，外包负责批量生产 | 速度和质量较平衡 | 外包质量波动，需要强验收 |
| 外部工作室主包 | 资产量大且需求稳定 | 工作室提供制作团队，项目方保留技术美术和监制 | 管理成本较低、产能高 | 容易变成“渲染图交付”，技术接入不足 |

对于 Ice Snow City，建议采用第二种模式：核心小队掌握视觉和技术标准，外部工作室只承担已经被模板化的批量资产。不要在没有首个标准资产和验收表之前就把 26 个真实资产整体外包。

## 八、90 天落地计划

| 时间 | 目标 | 交付 |
|---|---|---|
| 第 1–2 周 | 招募/确定美术总监、技术美术、环境主美 | 视觉 DNA、色板、镜头、尺度和性能预算 |
| 第 3–4 周 | 完成城市核心和银行灰盒 | Babylon.js 灰盒场景、交互挂点、初版 LOD |
| 第 5–7 周 | 完成城市核心高保真版本 | GLB、PBR、雪层、LOD、碰撞、引擎截图 |
| 第 8–9 周 | 完成角色和 NPC 标准 | 完整角色、共用骨骼、待机/行走、NPC 变体 |
| 第 10–11 周 | 完成商业中心、生产设施和道路包 | 可复用模块、地标变体和场景整合 |
| 第 12 周 | 真机回归和资产门禁评审 | iOS/Android 证据、缺陷清单、是否进入 verified 的决定 |

## 九、最容易失败的地方

第一，团队只招聘“会做漂亮模型”的人，却没有技术美术或引擎整合负责人。结果是模型在 DCC 软件里很好看，进入 Babylon.js 后材质、透明、动画或性能全部失控。第二，项目一开始同时制作几十个资产，导致每个资产都没有标准，最终只能得到一批风格不一致的半成品。第三，把 AI 生成图或程序化 GLB 当作最终高保真资产，跳过拓扑、UV、骨骼、碰撞和真机验证。第四，只用聊天记录管理版本，几个月后无法确认哪个文件有授权、哪个版本能运行。第五，用“艺术家说已经完成”代替可重复的验收证据。

## 十、给你的直接执行建议

当前最合理的启动方式不是立即招聘十几个人，而是先建立一个小型的**美术核心单元**：一名美术总监、一名技术美术、一名环境/建筑主美、一名角色主美，再配一名资产制作人或项目协调员。让这五个人在 30 天内共同完成“城市核心”这一件标准资产，并把完整制作流程、文件结构、验收脚本、真机采样和返工规则固化下来。

之后再将银行、商业中心、生产设施、道路和 NPC 交给经过试题验证的外部成员或工作室。所有外部交付都必须先通过内部技术美术审查，且不得直接修改真实资产 manifest 的高保真状态。只有真实资产包、性能证据包和许可证资料完整后，才允许从 `external-pending` 申请进入 `verified`。

### 建议的第一周行动表

| 日期 | 行动 | 结果 |
|---|---|---|
| 第 1 天 | 固定视觉 DNA、首批八类资产和性能预算 | 形成一页项目美术章程 |
| 第 2 天 | 发布环境主美、技术美术和角色主美招聘任务 | 候选人筛选标准统一 |
| 第 3 天 | 准备付费冰雪银行试题和验收表 | 能够横向比较候选人 |
| 第 4–5 天 | 审核作品集并进行技术面谈 | 只保留能提供线框、PBR、LOD 和引擎证据的人 |
| 第 6–7 天 | 选定核心成员，开始城市核心灰盒 | 从一个标准资产建立完整生产闭环 |

## 结论

高质量美术团队的本质是“视觉负责人 + 技术美术 + 可重复管线 + 严格验收”，而不是人数最多或单张渲染图最华丽。Ice Snow City 应先用核心小队建立一个可运行的标准资产，再通过模板化和外包扩产。这样既能保持冰雪都市的视觉统一，也能确保每一个真实资产最终能够在移动设备上稳定加载、渲染和维护。

本指南不会改变当前项目的外部 pending 状态，也不会把程序化 baseline 视为真实高保真证据。
