# Ice Snow City 项目现状与有序推进计划

**报告日期：** 2026-09-21  
**项目状态：** AI-generated development baseline 已完成；外部证据门禁保持关闭  
**报告目的：** 统一当前项目状态，避免重复开发，按照重要性推进剩余工作。

## 一、结论

Ice Snow City 当前不是“核心功能空白”状态，而是已经完成了可运行的游戏原型、基础 GameFi 交互、Babylon.js 场景、任务与 NPC 系统、模拟交易流程、AI 基线资产质量门禁和自动化测试体系。当前主要缺口集中在三类外部事实：真实高保真美术资产、真实 iOS/Android 性能证据，以及 GitHub 账户侧历史 Token 的撤销与轮换。

当前外部待办分类器确认共有 **18 项**，其中高保真资产 14 项，真实设备 1 项，账户安全 3 项，未知项为 0。由于这些材料或账户动作不在代码仓库内，不能通过继续编写模拟数据来安全关闭门禁。

因此，后续工作采用两条并行轨道：一条轨道继续完成可由代码和自动化验证闭环的本地工作；另一条轨道保持外部门禁 fail-closed，并准备好收到材料后的导入、验证和发布流程。

## 二、已完成的核心能力

### 1. 可玩游戏基础

项目已具备 React 19 与 Babylon.js 的 3D 运行基础，并使用 16:9 移动横屏作为目标布局。GameHub 作为主要游戏入口，已经承载场景、地标建筑、NPC 占位模型、任务追踪、任务大厅对话、路线点亮任务、区域解锁和金融区探索流程。

建设、收益、商店、背包、物品回收、建筑放置、升级、一键收取、资产面板和收取提示等模拟经济交互已经完成。收益参数已按长期运营目标显著下调，当前仅属于游戏内模拟数据，不代表真实 ISC 经济参数或主网资产价值。

### 2. Web3 与模拟交易基础

项目已经完成 EIP-712 订单构造与签名示例、订单提交和取消、交易列表筛选排序、立即购买、Make Offer、收到的出价、模拟链上交易历史、费用分配、状态推送、断线重连、Toast、详情日志、复制、失败重试和批量重试等开发环境流程。

当前链上流程仍处于模拟或只读边界。真实合约审计、生产部署地址、字节码验证、权限清单和真实资金写入门禁未被模拟结果替代。

### 3. 资产与质量门禁

已建立 procedural-baseline 资源包，并完成 8 个开发替代 GLB 的结构与完整性校验。已建立资产 manifest、GLB/PBR/LOD/碰撞/动画/纹理预算、Babylon.js 加载、来源安全和外部交付包校验规则。地块与建筑属于游戏内资产，不作为 NFT 核心资产；GLB/PBR 仅代表视觉交付证据。

`/admin/ai-baseline` Owner-only 仪表盘已经能够展示自动化测试矩阵、资产状态、软件性能趋势、pending 边界，并支持 CSV/PDF 导出。该页面展示的是开发基线质量，不会把 procedural-baseline 误标为高保真交付。

### 4. 测试与工程基线

历史完整回归已达到 205 个测试文件、2170 项测试通过。当前新增的 GitHub Token 检查工具包含 7 项 Python 单元测试，测试使用 mock，不访问 GitHub，也不需要真实凭据。

类型检查、生产构建、外部 pending 分类器、交付包安全扫描和 git diff 检查已经建立为可重复执行的门禁。项目还新增了 Token 到期检查的 package 命令和每周/手动 GitHub Actions 工作流；该工作流只执行只读 API 检查，不执行远程写操作。

## 四、按重要性排列的推进顺序

### P0：先保持安全与发布边界

第一优先级是保持真实主网写入、真实资金流程和高保真资产发布门禁关闭。所有 procedural-baseline、ci-software 和模拟合约结果都必须继续标记其证据等级。任何 Token 都不得写入仓库、脚本参数、日志或聊天内容。

账户侧历史 Token 撤销与轮换完成后，只需在受控环境更新 `ISC_GITHUB_TOKEN` 和到期登记信息，再运行只读检查。该检查不能替代 GitHub 账户侧的撤销动作。

### P1：完善本地可交付基线

第二优先级是完成可由本地代码闭环的质量工作，包括保持全量测试、类型检查、生产构建、外部交付包校验和 release gate 稳定运行；继续维护 Token 检查工具、定时工作流和文档；确保开发服务和 GameHub 入口没有回归；持续修复影响启动、路由、移动横屏和 Babylon 生命周期的本地问题。

本阶段的完成标准是：代码验证全部通过，工作区无意外敏感文件，所有自动生成结果都有明确来源和证据边界，且外部 pending 数量没有被错误减少。

### P2：收到资产后的导入验收

收到真实资产后，按以下顺序处理：先验证 SHA-256、MIME、文件路径和 glTF 结构；再验证网格面数、PBR 贴图、LOD、碰撞体和动画命名；随后在 Babylon.js NullEngine 与浏览器运行时验证加载；最后在移动设备上测量内存、首屏时间和稳定性。

真实文件通过上述门禁后，才允许更新 manifest 的运行时状态，并补充真实文件回归测试。资产交付前不应修改为 verified。

### P3：收到设备数据后的性能验收

设备数据必须分别覆盖 baseline 与 snow 模式，并记录设备型号、系统版本、浏览器、渲染器、屏幕方向、FPS、P95 帧时间、掉帧率、内存和采样持续时间。数据先经过敏感字段扫描和 schema 校验，再进入性能分析器和 GitHub Actions。

`ci-software` 只能用于流程演练，不能用于关闭真实设备门禁。设备证据通过三轮采样和稳定性要求后，才可以更新发布报告。

## 六、用户只需要处理的外部事项

用户不需要提供新的代码。需要处理的只有两类账户/材料事项：第一，确认历史 GitHub Token 已在 GitHub 设置中撤销，并使用有限期、最小权限的 Fine-grained Token 替代；第二，如果目标是高保真上线，需要准备真实 GLB/PBR/动画交付包和真实 iOS/Android 性能 JSON。

在这些材料到位前，项目可以继续进行本地开发和自动化质量收口，但不能诚实地宣称已经完成最终美术验收、真机验证或账户安全门禁。

## 七、当前验收口径

项目当前应标记为：**Local-Ready, External-Pending**。这表示本地开发基线可运行、可测试、可审计，外部发布所需的真实资产、真实设备和账户侧安全证据仍未完成。该状态不是失败，而是为了避免使用模拟证据误导发布决策。
